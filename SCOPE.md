# FocusFlow — Project Scope

## 1. Product overview

FocusFlow is a personal hierarchical object/work system where every unit of activity is a **Focus**, and domain-specific behavior is added through typed **Specifications**.

The initial system is designed for one user and very low traffic.

The core idea is:

> Everything is a Focus.

A Focus can contain child Focuses. A root Focus — a Focus without a parent — is called a **Flow**.

Example:

```text
Job Search
├── Workato
│   ├── HR Interview
│   ├── Technical Interview
│   └── Final Interview
└── Another Company
```

`Job Search` is a Flow. Every node in the tree is still a Focus.

The system starts generic. The first domain-specific Specification is implemented only after the generic system is usable.

---

## 2. Core entities

The initial persistence model contains these tables:

```text
focus_object
focus_goal
focus_goal_link
focus_specification
focus_event
```

There is no separate Flow table.

There is no tags table.

---

## 3. Focus

Table:

```text
focus_object
```

Fields:

```text
id UUID PRIMARY KEY
parent_id UUID NULL REFERENCES focus_object(id)
name TEXT NOT NULL
status TEXT NOT NULL
tags TEXT[] NOT NULL DEFAULT '{}'
description TEXT NULL
feedback TEXT NULL
color TEXT NULL

created_at TIMESTAMPTZ NOT NULL
updated_at TIMESTAMPTZ NOT NULL
finished_at TIMESTAMPTZ NULL
```

IDs use UUIDv7 and are generated by the application.

### Statuses

Supported Focus statuses:

```text
idea
planned
active
paused
waiting
done
cancelled
```

Semantics:

- `idea` — worth tracking, but there is no concrete plan yet.
- `planned` — there is a concrete plan/intention, but work has not started.
- `active` — currently in progress.
- `paused` — intentionally paused by the user.
- `waiting` — blocked on an external response, event, person, or dependency.
- `done` — successfully completed.
- `cancelled` — intentionally abandoned.

`done` and `cancelled` are terminal statuses.

When a Focus enters a terminal status, set `finished_at`.

When it returns from a terminal status to a non-terminal status, clear `finished_at`.

### Hierarchy

`parent_id = NULL` means the Focus is a Flow.

Focuses form an arbitrary-depth tree.

The backend must prevent cycles.

Deleting a Focus hard-deletes its entire descendant subtree.

---

## 4. Tags

Tags are arbitrary strings, not enums and not entities.

They are stored directly on `focus_object`:

```sql
tags TEXT[] NOT NULL DEFAULT '{}'
```

No tag table is introduced in v1.

---

## 5. Feedback

`feedback` is a nullable text field on Focus.

It is intentionally simple in v1.

Typical use cases:

- feedback from a colleague;
- recruiter/HR feedback;
- personal retrospective/comment after completion.

It is not a separate comment/history model.

---

## 6. Goal

Table:

```text
focus_goal
```

A Goal is owned by exactly one Focus.

Fields:

```text
id UUID PRIMARY KEY
focus_object_id UUID NOT NULL REFERENCES focus_object(id) ON DELETE CASCADE

type TEXT NOT NULL
description TEXT NOT NULL
status_override TEXT NULL

created_at TIMESTAMPTZ NOT NULL
updated_at TIMESTAMPTZ NOT NULL
finished_at TIMESTAMPTZ NULL
```

Supported Goal types in v1:

```text
primary
secondary
```

Deleting the owner Focus deletes the Goal.

### Goal status

`status_override` is nullable.

When it is set, it takes precedence over any derived state.

When it is not set:

- with no linked Focuses, the Goal has no derived state and is manually controlled;
- with one linked Focus, the Goal state is derived from that Focus;
- with multiple linked Focuses, the Goal exposes progress derived from the linked Focus statuses.

The exact response model for computed Goal progress must be explicitly defined in OpenAPI during the Goal API implementation.

Do not persist computed status distributions.

---

## 7. Goal-to-Focus links

Table:

```text
focus_goal_link
```

Fields:

```text
goal_id UUID NOT NULL REFERENCES focus_goal(id) ON DELETE CASCADE
focus_object_id UUID NOT NULL REFERENCES focus_object(id) ON DELETE CASCADE
PRIMARY KEY (goal_id, focus_object_id)
```

Create separate indexes on:

```text
goal_id
focus_object_id
```

A Goal may link to zero, one, or many Focuses.

Deleting a linked Focus deletes only the relation. It must not delete the Goal or any other linked Focus.

Deleting a Goal deletes its links.

Deleting the Goal owner Focus deletes the Goal and therefore all links owned by that Goal.

For multiple linked Focuses, progress is grouped by Focus status.

A multi-Focus Goal is fully resolved when all linked Focuses are terminal.

It is fully successful when all linked Focuses are `done`.

---

## 8. Focus Specification

Table:

```text
focus_specification
```

Fields:

```text
id UUID PRIMARY KEY
focus_object_id UUID NOT NULL REFERENCES focus_object(id) ON DELETE CASCADE

type TEXT NOT NULL
schema_version INTEGER NOT NULL
data JSONB NOT NULL

created_at TIMESTAMPTZ NOT NULL
updated_at TIMESTAMPTZ NOT NULL
```

A Focus may have multiple Specifications.

The generic storage layer does not assume that only one Specification exists per Focus.

### Strong typing requirement

The database stores Specification payloads in JSONB, but the public API is strongly typed.

Every supported Specification type must be represented in `contracts/openapi.yaml`.

The API contract uses a discriminated union, conceptually:

```yaml
FocusSpecification:
  oneOf:
    - $ref: '#/components/schemas/JobPositionSpecification'
    - $ref: '#/components/schemas/AnotherSpecification'
  discriminator:
    propertyName: type
```

Each variant contains a typed `data` model.

Adding a Specification type is a coordinated monorepo change that includes:

1. OpenAPI schema;
2. generated API types/client;
3. backend typed model and validation;
4. backend mapping to/from JSONB storage;
5. frontend renderer;
6. frontend editor if the type is editable;
7. tests.

There is intentionally no weakly typed `map[string]any` / arbitrary-object Specification contract at the API boundary.

### Generic system before the first Specification

The generic system is implemented before the first domain Specification.

Phase 1 may create:

- the table;
- storage abstraction;
- internal Specification infrastructure.

Do not expose a weakly typed public Specification CRUD API merely to have it early.

The first public typed Specification API is added together with the first concrete Specification type.

## 9. Focus Events

Table:

```text
focus_event
```

The purpose is activity/audit history and a future foundation for metrics and agent auditing.

This is not event sourcing.

Current state stays in normal tables.

Initial events may include:

```text
focus.created
focus.updated
focus.status_changed
focus.parent_changed

goal.created
goal.updated
goal.deleted
goal.link_added
goal.link_removed

specification.created
specification.updated
specification.deleted
```

Event source examples:

```text
web
api
system
```

Future source:

```text
mcp
```

The exact event payload schema should be defined during Phase 1 before implementation.

The read API and Activity UI are deferred to Phase 6, but mutation events should be recorded before that so history already exists.

## 10. API principles

REST API.

Base prefix:

```text
/v1
```

OpenAPI is the source of truth for the HTTP contract.

JSON fields use `camelCase`.

Database fields use `snake_case`.

Transport models, core/internal models, and PostgreSQL storage models are separate.

Business logic does not live in HTTP handlers.

### Flows

Flow is a business-level API abstraction over root Focuses.

```text
GET  /v1/flows
POST /v1/flows
```

`GET /v1/flows` returns Focuses with no parent.

`POST /v1/flows` creates a Focus with no parent.

There is no Flow persistence entity.

### Focuses

Initial direction:

```text
POST   /v1/focuses
GET    /v1/focuses/{id}
PATCH  /v1/focuses/{id}
DELETE /v1/focuses/{id}

GET    /v1/focuses/{id}/children
```

The exact request/response schemas are defined contract-first in OpenAPI during implementation.

### Goals

Initial direction:

```text
GET    /v1/focuses/{id}/goals
POST   /v1/focuses/{id}/goals

GET    /v1/goals/{id}
PATCH  /v1/goals/{id}
DELETE /v1/goals/{id}

POST   /v1/goals/{id}/focuses
DELETE /v1/goals/{id}/focuses/{focusId}
```

### Activity

Reserved for Phase 6:

```text
GET /v1/focuses/{id}/activity
```

Do not over-design the activity read model during Phase 1.

## 11. Pagination

Every endpoint whose primary response is a collection must use cursor pagination from its first implementation.

Do not add unpaginated collection endpoints and promise to fix them later.

Request shape:

```text
?limit=50&cursor=<opaque-cursor>
```

Defaults:

```text
default limit = 50
maximum limit = 100
```

Response shape:

```json
{
  "items": [],
  "count": 0,
  "nextCursor": null,
  "hasMore": false
}
```

`count` is the number of items in the current response, not the total database count.

Do not run a separate total `COUNT(*)` unless a product requirement needs it.

Cursors are opaque to clients.

Ordering must be deterministic and use a stable unique tie-breaker.

## 12. Authentication

There is no users table in v1.

Authentication uses one login/password pair configured through environment variables.

Configuration:

```text
APP_USERNAME
APP_PASSWORD_HASH
APP_TOKEN_SECRET
```

`APP_PASSWORD_HASH` uses Argon2id.

Provide:

```text
backend/cmd/hash-password
```

The command reads a password from stdin and prints an encoded Argon2id hash.

Do not require plaintext passwords as command-line arguments.

Initial endpoints:

```text
POST /v1/auth/login
POST /v1/auth/logout
GET  /v1/auth/me
```

Successful login issues a signed token transported in an HttpOnly cookie.

Production cookie settings must support the actual Vercel/Railway deployment topology.

CORS uses explicit configuration.

Local development must work without manual CORS troubleshooting.

No registration, password reset, OAuth, RBAC, or user management is implemented in v1.

---

## 13. Backend architecture

Backend:

```text
Go
PostgreSQL
pgx
goose
OpenAPI
oapi-codegen
Docker
```

Models are separated into layers:

```text
API/generated models
        ↓
core/internal models
        ↓
storage interface
        ↓
PostgreSQL storage models
```

Additional internal typed models may be introduced for a specific Specification or subsystem.

Storage is represented by Go interfaces.

PostgreSQL packages implement those interfaces.

Storage interfaces receive/return core/internal models, not API or PostgreSQL-specific models.

Avoid enterprise abstractions that do not create a real boundary.

HTTP is an adapter.

Future MCP must be able to call the same application services rather than duplicate business logic.

---

## 14. Frontend architecture

Frontend:

```text
Next.js
React
TypeScript
Tailwind CSS
```

The frontend runs directly with Node.js during development.

It is not containerized for local development.

It consumes generated types/client from the OpenAPI contract.

Do not manually duplicate backend DTOs in TypeScript.

Specification renderers/editors are explicit code components selected by the typed Specification variant.

Do not build a schema-generated generic UI framework in v1.

---

## 15. OpenAPI contract

Source of truth:

```text
contracts/openapi.yaml
```

Generated artifacts are committed.

Expected direction:

```text
contracts/openapi.yaml
    ├── backend/internal/api/generated/
    └── frontend/src/api/generated/
```

CI regenerates both outputs and fails if generated code differs from committed files.

A Specification contract change must update backend and frontend in the same repository change.

---

## 16. Database migrations

All schema changes use goose.

Migration files live in:

```text
backend/migrations/
```

Every normal SQL migration contains both directions:

```sql
-- +goose Up
...

-- +goose Down
...
```

Migrations are committed with the backend source.

Development, CI, and production all use the same migration files.

No manual production schema edits.

---

## 17. Local development topology

The user does not want a local PostgreSQL instance.

Local development is:

```text
Browser
   ↓
Next.js dev server
http://localhost:3000
   ↓
Go backend in Docker
http://localhost:8080
   ↓
Railway PostgreSQL public endpoint
```

The frontend runs directly with Node.js.

The backend runs through:

```text
docker-compose.local.yml
```

The local Compose file contains the backend only.

It does not start PostgreSQL.

The local backend uses a local `.env.local` file containing a database URL suitable for external access to the Railway Postgres instance.

The standard local frontend origin must already be configured for CORS by the local Compose configuration.

Do not require the user to disable browser security or manually modify headers for normal local development.

---

## 18. Production topology

```text
Vercel
  └── frontend

Railway
  ├── backend
  └── PostgreSQL
```

Frontend and backend deploy independently.

Railway builds the backend from `backend/Dockerfile`.

Railway production deployment does not depend on Docker Compose.

The backend Railway service gets `DATABASE_URL` through a Railway reference variable pointing to the PostgreSQL service.

Database migrations run through goose as a Railway pre-deploy command.

If migration fails, deployment must fail.

---

## 19. CI/CD

Use GitHub Actions.

CI runs on pull requests and pushes to `main`.

### Contract checks

- validate OpenAPI;
- regenerate Go API code;
- regenerate TypeScript API code/client;
- fail on generated-code drift.

### Backend checks

- formatting;
- lint/static analysis;
- `go vet`;
- unit tests;
- integration tests when persistence is involved;
- build;
- Docker image build;
- goose migration validation.

### Database tests

The developer does not run PostgreSQL locally.

CI may and should use a disposable PostgreSQL service/container for integration tests.

### Frontend checks

- dependency install from lockfile;
- lint;
- typecheck;
- tests;
- production build.

### Deployment

- Vercel deploys frontend.
- Railway deploys backend from Dockerfile.
- Railway waits for CI before production deployment.
- Railway pre-deploy runs goose migrations.

## 20. Implementation phases

### Phase 0 — Repository foundation

Create the repository skeleton and development/deployment foundation.

### Phase 1 — Core backend

Implement authentication, Focus, Goal, Goal links, Specification infrastructure, Events, persistence, services, REST API, hierarchy protection, pagination, and tests.

No domain Specification type yet.

### Phase 2 — Generic UI

Implement login, application shell, Flow list/cards, and create Flow.

### Phase 3 — Focus page

Implement Focus details, breadcrumbs/hierarchy, children, Goals, and the base area where typed Specification blocks will later render.

### Phase 4 — Editing

Implement generic editing for Focus, hierarchy, tags, status, description, feedback, color, Goals, and Goal links.

### Phase 5 — First Specification

Define and implement the first domain Specification for job-search/job-position tracking.

The exact contract is designed at the start of this phase.

### Phase 6 — Activity

Expose stored events through a typed read API and build Activity UI.

### Phase 7 — Observability

Add structured logs, request IDs, latency/error visibility, DB timing, and then OpenTelemetry where useful.

### Phase 8 — MCP

Add an MCP adapter over the existing application services.

## 21. Explicitly out of scope

Do not implement without explicit approval:

- multiple users;
- registration;
- invitations;
- password reset;
- OAuth;
- RBAC;
- organizations/workspaces;
- billing;
- mobile applications;
- offline mode;
- real-time synchronization;
- WebSockets;
- optimistic locking;
- collaborative editing;
- Redis;
- queues;
- Kafka;
- microservices;
- Kubernetes;
- GraphQL;
- event sourcing;
- CQRS;
- `ltree`;
- separate tag entities;
- local developer PostgreSQL;
- schema-generated dynamic frontend;
- arbitrary user-created Specification schemas;
- public API keys;
- MCP before Phase 8.

---

## 22. Planned, but not initial scope

The design should not block:

- more typed Specification types;
- Flow/Focus metrics;
- event-derived analytics;
- MCP access;
- iOS/Android clients;
- database-backed multi-user authentication;
- family/friend invitations;
- eventual public registration.

Do not implement these prematurely.
